# fsh — спецификация

Дата: 2026-08-14. Статус: утверждено пользователем (a.latipov).

Это спецификация базового CLI. Спецификация проекта целиком — [PLAN.md](../PLAN.md); при расхождении прав PLAN.md.

## Задача

CLI-обёртка над `glab` для повседневной работы с MR в GitLab. Не привязана к конкретному GitLab-инстансу: repo/host настраиваются. Должна одинаково хорошо работать из терминала человека и из AI-агентов (детерминированный вывод, флаг `--json`, понятные ошибки).

## Нефункциональные требования

- Node.js ESM. **Ноль новых внешних программ** — это ограничение жёсткое; npm-библиотеки при этом можно, их ставит `npm ci`. Внешние бинари: `node`, `git` (≥2.38), `glab`, `claude`. Плюс базовые системные: `security` (ключи в keychain)
и `cp -Rc` для переноса `node_modules` в worktree — это macOS-специфика (APFS clonefile), у GNU `cp` флага `-c` нет.
- Все данные — через `glab api` (JSON), никакого парсинга человекочитаемого вывода `glab` (кроме команды создания worktree — это `git`).
- Команды ждут асинхронные операции (пайплайны, джобы) с анимацией: спиннер + живой статус джоб, опрос каждые 5 секунд.
- Ошибки — понятные сообщения с подсказкой «что сделать», exit code ≠ 0.
- Конфиг: `~/.config/gl-helper/config.json`. Приоритет: флаг CLI > env (`GL_HELPER_REPO`, `GL_HELPER_HOST`) > конфиг. Без настроенных repo/host glab-команды падают с подсказкой `config init`.

## Команды

| Команда | Описание |
|---|---|
| `mrs [фильтры]` | Открытые MR: iid, title (+Draft), `source→target`, статус head-пайплайна, комментарии (всего / открытых тредов / решённых), конфликт есть/нет |
| `mr <ветка\|номер>` | Один MR в том же формате. Поиск по части имени ветки (неточное, case-insensitive) среди открытых MR; также принимает `!2547` и `2547` |
| `conflict <mr\|ветка> [--agent claude\|pi]` | Решить конфликт силами агента (см. ниже) |
| `threads <mr\|ветка> [--agent claude\|pi]` | Разобрать нерешённые треды ревью силами агента (см. ниже) |
| `review <mr\|ветка> [--agent claude\|pi]` | Ревью диффа MR по правилам проекта (читающее) |
| `analyze <KEY> [--agent claude\|pi]` | Разбор задачи Jira по коду проекта (читающее) |
| `jira [mine\|<KEY>\|move <KEY> <статус>\|field <KEY> "<поле>" <значение>]` | Задачи Jira: список с фильтрами `--assignee/--sprint/--component/--status/--jql`, задача с комментариями, смена статуса, запись любого поля |
| `growthbook [list\|get <id>\|create <id> <on\|off>\|toggle <id> <on\|off>]` | Фича-флаги GrowthBook: список, один флаг, создание, включение и выключение в окружении |
| `task start <KEY>` / `task push [KEY]` / `task judge [KEY]` | Взять задачу в работу (ветка по шаблону проекта), запушить её с открытием MR, показать приёмку судьи (см. ниже) |
| `jobs <mr\|ветка>` | Джобы последнего MR-пайплайна: stage, имя, статус, id. Устаревший или отсутствующий пайплайн пересоздаётся (`POST .../pipelines`) — команда не read-only |
| `run <джоба> <mr\|ветка>` | Запустить manual-джобу по имени (или id) в последнем MR-пайплайне |
| `deploy <ветка\|mr> [N]` | build → ждать успеха → запустить `deploy_dev` (или `deploy_dev2…10`) → ждать итога |
| `watch` | Один опрос: дифф с прошлым снимком, триаж судьёй, уведомление (действий не запускает) |
| `tui` | Полноэкранный режим на ink: вкладки MR / задачи / история запусков, действия и пайплайны с клавиши (см. ниже) |
| `flow [list\|show <имя>]` | Сценарии работы для агента: пошаговые протоколы с командами fsh (см. ниже) |
| `config init` / `config show` / `config migrate` | Создать/показать конфиг, перевести v1 на v2 |
| `help` | Список команд с примерами |

Флаги: `-R/--repo`, `--json` (read-команды), `--agent` (действия), `-B/--build-job` (deploy, дефолт `build_image`).

## Конфликт: цепочка

1. Резолв MR, `git fetch origin <source> <target>` в `projectDir` из конфига.
2. `git merge-tree --write-tree --name-only --no-messages origin/<target> origin/<source>`: exit 1 → конфликт, exit 0 → чисто. Первая строка stdout — OID дерева, отбрасывается; остальные строки — конфликтующие файлы. Нет конфликта → сообщить и выйти. Поле `has_conflicts` из GitLab не используется: при `unchecked` оно врёт.
3. Временный worktree: `~/.local/state/fs-harness/worktrees/<проект>/conflict-<iid>-<ts>` (рут вне репозитория проекта), внутри — ветка `fs-harness/conflict-<iid>-<ts>`. `node_modules` переносятся клоном (`cp -Rc`); если lock-файл ветки разошёлся с чекаутом, `deps_available: false` и промпт честно говорит агенту, что линта и тестов у него нет.
4. Агент (claude или pi, headless `-p`) работает **только внутри worktree**, cwd = worktree. Промпт (утверждён):
   - данные MR: номер, URL, ветки `source→target`, worktree уже готов, список конфликтующих файлов;
   - шаги: `git merge origin/<target>`, решить конфликты вручную, сохраняя функциональность обеих веток (приоритет равный), запрещены «взять всё ours/theirs» и force-push;
   - верификация: линт и unit-тесты проекта перед коммитом;
   - коммит по правилам проекта (посмотреть `git log` и повторить стиль);
   - **push агенту запрещён** — его делает fsh после приёмки;
   - конфликтов нет — просто сообщить, ничего не коммитить.
5. `verify`: механические факты о результате — коммиты впереди `origin/<source>`, `head_sha`, изменённые файлы, остатки маркеров конфликта, `git diff base..HEAD`. Коммитов нет → ошибка.
6. Судья (роль `acceptance`) получает цель, факты, дифф и текст агента. Вердикт `revise` возвращает работу агенту в ту же сессию (`claude --resume`, `pi --session-id`) вместе с находками, дальше факты и вердикт снимаются заново; повторов не больше `judge.maxRevise` (дефолт 1). **Push происходит только при `approve`**; любое другое решение, невалидный вердикт или падение бэкенда закрывают гейт: worktree сохраняется (как и при любом провале после запуска агента), коды `judge_rejected`, `judge_schema`, `judge_failed`. `--no-judge` отключает приёмку явно.
7. `publish`: `git push origin HEAD:<source>` с read-back проверкой, что origin встал на `head_sha`.
8. Пайплайн build жмёт **fsh**, не агент: если head-пайплайн MR устарел (sha ≠ нового HEAD) — создать новый MR-пайплайн, найти build-джобу, запустить, дождаться, показать статус.
9. **Гарантированная очистка** (finally): `git worktree remove --force` + `git worktree prune` + удаление временной ветки.

## Треды: цепочка

1. Резолв MR, `git fetch origin <source>`, `GET /merge_requests/<iid>/discussions`.
2. Открытым считается тред, где есть хоть одна заметка `resolvable && !resolved && !system`. Открытых нет → `skipped`, агент не запускается.
3. Временный worktree, как у `conflict` (`threads-<iid>-<ts>`).
4. Агент получает тексты тредов с файлом и строкой, правит код там, где ревьюер прав, и пишет тексты ответов в `replies.json` рана: массив `{id, reply, resolve}`. Push, `glab` и отправка ответов агенту запрещены.
5. `verify`: коммиты впереди `origin/<source>` (ноль — норма, тред мог требовать только ответа), `head_sha`, дифф, разбор `replies.json`. Файла нет или он не по формату → `agent_failed`. Треды без ответа и ответы на неизвестные id идут в факты судье.
6. Судья (роль `acceptance`) видит цель, факты, тексты тредов и подготовленные ответы. **Ответы уходят только при `approve`.**
7. `publish`: если были коммиты — `push` с read-back; затем по каждому треду `POST .../discussions/<id>/notes` и, если агент пометил `resolve`, `PUT .../discussions/<id>?resolved=true`. Обе операции с read-back проверкой. Ответы на неизвестные треды пропускаются.
8. Build-пайплайн `threads` не жмёт: это дело `conflict` и `deploy`.

## Конфиг: две версии

Читается `~/.config/fs-harness/config.json`, если он есть, иначе `~/.config/gl-helper/config.json` —
путь рабочего файла намеренно не переехал вслед за именем пакета.

v1 (плоские `repo`, `host`, `projectDir`) мигрируется **в памяти** при каждом запуске: имя проекта =
`basename(dir)` либо второй сегмент `repo`, поля переезжают внутрь `projects.<имя>`, общие настройки
(`agentArgs`, `judge`, `workspace`) остаются наверху. На диск ничего не пишется, пока владелец не
выполнит `fsh config migrate` — она печатает «было/станет», спрашивает и оставляет рядом `.v1.bak`.

Активный проект: `-P <имя>` > `FS_HARNESS_PROJECT` > `activeProject` > единственный в файле. Поля
активного проекта раскладываются в плоские `cfg.repo`, `cfg.host`, `cfg.projectDir`, `cfg.jira`,
`cfg.agent` — команды про мультипроектность не знают. Проектный `deps` перебивает общий
`workspace.deps`.

## Читающие действия: review и analyze

Оба идут в режиме изоляции `checkout`: рабочий каталог — сам `projectDir`, git-операций нет.
Движок снимает `git rev-parse HEAD` + `git status --porcelain` до и после и падает с `dirty_checkout`,
если действие что-то изменило. Push и публикация не предусмотрены вовсе.

- `review`: дифф берётся из API GitLab (`GET /merge_requests/<iid>/changes`), а не из локального git —
  фетчить чужие ветки в живой чекаут нельзя. Правила ревью читаются из `.claude/skills/mr-review/SKILL.md`
  проекта (нет файла — встроенный минимум). Судья в роли `mr-review` — `advisory`: смотрит тот же дифф
  и те же правила, печатает второе мнение, ничего не блокирует. Изменений в MR нет → `skipped`.
- `analyze`: цель действия — задача Jira (`target: 'issue'`, ключ по форме `FD-7647`). Читаются задача
  (v2, description текстом) и её комментарии. Судьи нет: разбор ничего не публикует.

## TUI

Голый `fsh` в живом терминале открывает TUI; в пайпе, с `--json` и в MCP остаётся текст и справка
(`tui_requires_tty`, если позвать `fsh tui` без терминала).

- Состояние — чистое (`src/tui/store.js`): `reduce(state, action)` и `keyIntent(input, key, state)`
  тестируются без ink. Экран (`src/tui/app.js`) только рисует то, что отдал reduce.
- Видно, чем экран занят: каждый запрос к GitLab и Jira оборачивается подписью, и пока он идёт,
  в шапке крутится спиннер с ней («треды, аппрувы и пайплайны 13с»). После трёх секунд дописывается
  счётчик. Панели пайплайна, переходов и спринтов открываются сразу и наполняются по приходу данных.
- Транспорт `glab` асинхронный (`execFile`, не `execFileSync`): синхронный запуск держал event loop,
  и TUI не перерисовывался и не слышал клавиш всё время запроса. Побочно `mapLimit` в `mrs` наконец
  работает параллельно — список с бейджами собирается секунды, а не полминуты.
- Экран занимает окно терминала целиком: высоты блоков считаются от `stdout.rows` и пересчитываются
  на ресайз. `Tab` переносит фокус (список → детали → лог), `j`/`k` и `PgUp`/`PgDn` двигают курсор в
  списке и прокручивают тот блок, который в фокусе. У лога отсчёт прокрутки от конца.
- Три вкладки (`1-3`): **MR** (`mrs`), **Задачи** (`jira mine`), **История** (журнал прошлых запусков
  из `~/.local/state/fs-harness/runs`: что запускали, вердикт судьи, цена, каталог рана).
- Строка MR двухэтажная, как в списке GitLab: заголовок с бейджами справа (статус пайплайна,
  `✅Approved`, `💬N of M` по тредам, `⚠конфликт`) и ниже `!iid · создан … · автор · метки`.
  Список грузится в два захода: сперва сами MR, следом бейджи (треды и аппрувы — запрос на каждый MR).
- `f` — панель фильтров списка MR: те же поля, что у флагов CLI. Enter задаёт значение или
  переключает флаг, Backspace сбрасывает поле, Esc применяет и закрывает. Активные фильтры видны
  в строке подсказок.
- Действия с клавиши по выбранному MR: `a` — conflict, `t` — threads, `r` — review, `p` — панель
  пайплайна. Каждый запуск — карточка: фаза, цена, последняя строка агента.
- `E` — правка полей MR: заголовок, описание (в `$EDITOR`), assignee, ревьюеры (логины через запятую,
  id ищутся среди участников проекта), метки, target branch, squash, удаление ветки после мержа.
  Каждое поле уходит отдельным `PUT /merge_requests/:iid`, список после этого перечитывается.
- По выбранной задаче: `n` — analyze, `s` — смена статуса списком переходов, `S` — перенос в спринт,
  `c` — комментарий, `e` — раскрыть длинные поля, `p` — окно родителя со всеми его подзадачами,
  `E` — правка любого поля из `editmeta`: списки выбираются, строки и числа набираются, описание и
  другой многострочный текст открывается в `$EDITOR`.
  В списке задача занимает несколько строк: ключ, статус и исполнитель (`нету`, если никого), под
  ними название до трёх строк, ниже метки и родитель. `←`/`→` двигают панели вбок, если хвост
  строки не влез. В карточке — Assignee, ответственные, Reporter, Priority, Labels, Sprint, Parent, Linked work
  items и свёрнутые блоки «Описание», «Technical details for QA», «Контент», «Комментарии».
- Панель пайплайна (`p`) показывает все джобы по стадиям, как в GitLab; `enter` запускает выбранную.
  `deploy_dev*` идёт через `cmdDeploy`: сперва `build_image`, если он ещё не собран, с ожиданием.
  Пока джоба идёт, панель перечитывается раз в 5 секунд.
- События `runAction` льются в лог (буфер сбрасывается раз в 100 мс, хранится 2000 строк): текст агента,
  дельты судьи, вердикт. `x` прерывает все живые раны, `o` открывает `web_url` выбранной строки,
  `q` выходит (при живых ранах — второе нажатие), `?` — помощь.

## Фильтры MR

`--author`, `--assignee`, `--reviewer` (значение `me` резолвится через `GET /user`), `--target`,
`--label`, `--search`, `--draft`/`--no-draft` уходят параметрами в `GET /merge_requests`.
`--conflicts`, `--threads` и `--pipeline <статус|none>` применяются после выборки: конфликт, открытые
треды и статус пайплайна в списке MR не приходят. Пустой результат под фильтрами говорит «под фильтры
не попал ни один MR», а не «в репозитории нет MR».

## Jira: фильтры, переходы, спринт и комментарий

Список собирается в JQL: `--assignee me|<почта>|any` (дефолт `me`), `--sprint current|<имя>`,
`--component <значение>` (имя поля — `jira.componentField`, дефолт «Компонент»), `--status <имя>`
(без него — `statusCategory != Done`), `--jql` перебивает всё. `jira move <KEY> <статус>` —
единственная запись: переход ищется по имени перехода или целевого статуса, спрашивается
подтверждение (`-y` снимает), после `POST .../transitions` статус перечитывается; не изменился —
ошибка `api_failed`. Переход с обязательными полями валидатора отвечает 400 со списком полей —
fsh их не заполняет.

Ещё две записи: `jira sprint <KEY> <спринт>` переносит задачу в спринт (доска берётся из текущего
спринта задачи, иначе ищется по ключу проекта; спринт выбирается по имени, вхождению или id) и
`jira comment <KEY> <текст>` публикует комментарий. Обе спрашивают подтверждение и понимают
`--dry-run`. Больше fsh в Jira не пишет.

`jira field <KEY> "<имя поля>" <значение>` — пятая запись, PUT произвольного поля. Значение берётся
из хвоста аргументов или из `--file <путь|->` (`-` — stdin: так в задачу кладут многострочный текст,
например результат скилла проекта). Имя поля человеческое, id считается из `editmeta`; форма
значения — по схеме поля (список строк через запятую, число, вариант из `allowedValues` по имени,
остальное текстом). Неизвестное имя отвечает списком правимых полей задачи, чужой вариант —
списком допустимых. После PUT задача перечитывается: пустое поле — ошибка `api_failed`, не успех.

Кастомные поля читаются по названию: задача запрашивается с `expand=names`, и «Ответственный
разработчик», «Technical details for QA», «Контент», «Sprint» находятся по имени, а не по
`customfield_10341` — id у каждого проекта свои.

## Задача: ветка и MR

`task start <KEY>` читает задачу и ставит рабочее дерево на ветку по шаблону проекта
(`branchPattern`, дефолт `feature/{key}`). Ветки нет — создаётся от `origin/<целевая>`; есть
локально — `switch`; есть только на origin — создаётся с отслеживанием; уже на ней — ничего не
делает. Незакоммиченные правки останавливают переключение (`dirty_checkout`): они уехали бы в чужую
ветку. Статус в Jira не двигается — это работа скилла проекта.

`task push [KEY] [--target <ветка>]` пушит текущую ветку в `origin` и открывает MR в целевую ветку
(дефолт — `targetBranch` проекта, иначе `dev`). Ключ берётся из имени ветки, если не передан.
Заголовок MR — `<KEY>: <название задачи>`, описание — ссылка на задачу, ветка удаляется после
мержа. Открытый MR из этой ветки не дублируется. Нет коммитов поверх целевой ветки — `no_commit`.

`task judge [KEY]` — приёмка: судья в роли `task-acceptance` сверяет дифф `origin/<целевая>...HEAD`
с текстом задачи и возвращает вердикт. Это совет, а не гейт: `push` он не блокирует. Ключ берётся
из имени ветки. `--dry-run` печатает payload, не тратя судью.

Первые две команды отказываются работать с защищёнными ветками (`dev`, `master`, `main`, `rel/*`,
`release/*`, целевая ветка проекта) и понимают `--dry-run`: он печатает список git-команд, ничего
не выполняя.

## Сценарии для агента

`src/prompts/flows/<имя>.md` — markdown-протоколы: `take-task` (взять задачу в работу),
`push-task` (запушить и открыть MR), `fill-jira` (обязательные поля задачи). `flow list` печатает
имена с описаниями из front-matter, `flow show <имя>` — текст протокола. Переопределяются как
промпты: проектный `<projectDir>/.fs-harness/prompts/flows/<имя>.md`, личный, встроенный. Список
сценариев попадает в `fsh agent-guide` отдельным разделом. Тест проверяет, что каждая упомянутая
в протоколе команда `fsh` есть в реестре.

## GrowthBook: фича-флаги

`growthbook.baseUrl` в конфиге проекта — адрес **API**, а не веб-интерфейса (у self-hosted это
разные хосты). Ключ читается из `~/.growthbook_apikey` третьим источником после env
(`FS_HARNESS_GROWTHBOOK`) и keychain. `growthbook list` склеивает страницы и не показывает
архивные флаги, `get <id>` — один флаг целиком, `create <id> [on|off]` заводит boolean-флаг,
`toggle <id> <on|off> [--env <окружение>]` включает или выключает его в окружении (дефолт —
`growthbook.env`, обычно `production`). Обе записи спрашивают подтверждение и понимают `--dry-run`.
После переключения флаг перечитывается: GrowthBook отвечает 200 и на окружение, которого у флага
нет, поэтому «принял, но не переключил» — ошибка `api_failed`. `doctor` проверяет доступ, если
`baseUrl` задан.

## Watcher

`fsh watch` — один опрос, без демона и расписания. Снимок (`fsh mrs` в виде объекта) лежит в
`~/.local/state/fs-harness/watch/<repo>.json`; битый файл равен отсутствию. `diffSnapshots` даёт
события `pipeline`, `threads`, `conflict`, `mr_new`, `mr_gone`; первый снимок событий не даёт.
Батч уходит судье в роли `event-triage`, тот на каждое событие возвращает `finding` с id события
в `file` и `severity` `blocker | warning | nit` (срочно / к сведению / шум). До канала доходят
не-`nit`; провал триажа — показываем все события и говорим об этом.

## Уведомления

`mattermost.webhook` (общий или на проект) — incoming webhook. Подписчик того же потока событий:
на `done` и на `error` шлёт `POST {text}` с одной строкой (действие, цель, решение судьи, цена,
ссылка). Провал POST — строка в логе рана, не ошибка действия. Ключей и бота нет; `doctor` проверяет
только форму адреса и в канал ничего не пишет.

## Архитектура

```
src/
  main.js        — разбор argv, dispatch, help
  glab.js        — обёртка glab api (все вызовы), exec инжектируется (тесты)
  resolve.js     — поиск MR по номеру/части ветки → объект MR
  config.js      — чтение/запись ~/.config/gl-helper/config.json
  ui.js          — спиннер, прогресс, перерисовка статусов, humanize времени
  format.js      — таблицы и строки вывода (текст/JSON)
  commands/      — по файлу на команду (mrs, mr, jobs, run, deploy, conflict, config)
  engine.js      — runAction: фазы действия, события, изоляция, гейт судьи
  actions/       — декларации действий (precheck/context/verify/publish)
  prompts.js     — шаблоны промптов: оверрайды, front-matter, строгие переменные
  secrets.js     — ключи: env → keychain → ошибка с командой заведения
  notify.js      — исходящие уведомления в Mattermost (incoming webhook)
  watch.js       — снимок состояния MR, дифф с прошлым, триаж судьёй
  agent/         — spawn (процесс агента), events (поток), journal (раны)
  judge/         — judge(), zod-схема вердикта, payload, провайдеры cli и openai
  tui/           — store (чистое состояние), app (ink + htm), index (старт и проверка TTY)
  prompts/judge/ — рубрики судьи, файл на роль
test/            — node --test, мокнутый exec: парсинг/логика без сети
```
